# Устойчивая отправка счетов: границы и эксплуатация

Реализовано для `send-invoice-email` и `send-invoice-reminder`. Это журнал
конкретных операций отправки, а не гарантия доставки во входящие и не общая
атомарность PostgreSQL, Redis и внешнего почтового сервиса.

## До включения новой версии worker

- Применить предыдущие incremental upgrades, включая резервирование платежей:
  оно добавляет `invoices(id, team_id)`, необходимый составному внешнему ключу.
- Применить `20261101060507_durable_invoice_email_delivery.sql` одним
  транзакционным запуском по общему runbook. Baseline не переписывать.
- Проверить права `agsaas_app` и отсутствие доступа к новой таблице у `anon`
  и `authenticated`. HTML, адреса, ссылки и PDF не являются публичными данными.
- Сначала выполнить репетицию обновления и восстановления из backup.
- Проверить старые задания Redis. Для уже начавшихся до обновления отправок
  журнал не восстанавливает историю задним числом. Пакет не разрешает слепую
  очистку очереди или повтор всех старых заданий.

## Как проходит отправка

1. Worker получает устойчивый ключ операции. Генерация PDF передает его
   дочернему заданию; повтор генерации использует тот же ключ. Версионная
   отложенная отправка привязана к точному marker расписания. Новое ручное
   действие или отдельное напоминание получает другой ключ.
2. До HTTP в PostgreSQL сохраняются полностью сформированные байты запроса:
   HTML, адреса, зашифрованная ссылка, заголовки и содержимое PDF. Сохраняется
   SHA-256. Повтор не строит письмо из изменившегося шаблона или Storage.
3. Короткая транзакция проверяет актуальный статус счета и расписание,
   захватывает операцию на 120 секунд и фиксирует время первой попытки.
   Ни скачивание, ни рендер, ни HTTP не выполняются под SQL-блокировкой.
4. Запрос использует один provider key `agsaas-invoice/<delivery UUID>`.
   HTTP ограничен 30 секундами; timeout не считается доказанным отказом.
5. Подтверждение провайдера сначала сохраняется в журнале. Затем отдельная
   атомарная транзакция обновляет счет, создает уведомления действующим
   участникам и отмечает операцию завершенной. Повтор этой транзакции не
   дублирует уведомления. Содержимое HTML/PDF удаляется из завершенной строки.

Общий предел сохраненного конверта составляет 4 MiB. PDF проверяется до
чтения в память с запасом на base64 и HTML. Если шаблон требует PDF, ошибка
его скачивания не превращается в отправку без вложения.

## Повторы и восстановление

Существующий invoice scheduler запускает `reconcile-invoice-deliveries`
каждую минуту, до 25 записей за проход. Он использует сохраненные операции,
а не создает новые письма. Поэтому потерянное Redis-задание после сохранения
конверта может быть восстановлено. Потеря первоначального задания до этого
момента пока не закрыта: нужен отдельный transactional enqueue outbox.

[Resend хранит ключи идемпотентности 24 часа](https://resend.com/docs/dashboard/emails/idempotency-keys).
Автоматический replay ограничен 23 часами от DB-времени перед первой
попыткой, максимум 12 provider attempts, с задержкой 60-900 секунд.
Неизвестный исход повторяется только с теми же байтами и ключом внутри этого
окна. После его окончания операция останавливается для сверки.

Наблюдаемое движение DB-часов назад, некорректные даты или нарушенный порядок
времени также останавливают replay. Время читается после захвата блокировки,
чтобы ожидание чужой транзакции не выглядело как движение часов назад.
Это защита от обнаруженной аномалии, не обещание распределенных идеальных
часов. Уже выполняющийся HTTP может вернуть настоящее подтверждение; его
исходный владелец вправе сохранить его по неизмененному lease token, но
не вправе вновь поставить остановленную операцию на отправку.

Если письмо уже принято, восстановление выполняет только локальную
финализацию, даже если счет позже оплатили. Ошибка финализации откладывает
следующий фоновый проход на 5 минут, чтобы одна поврежденная запись не
вытесняла остальные. Повторного HTTP для известного подтверждения нет.

## Состояния журнала

| Состояние | Значение |
| --- | --- |
| `pending` | Конверт сохранен; первая попытка либо безопасный повтор ожидает срока |
| `sending` | Операцией владеет lease; результат может быть еще неизвестен |
| `accepted` | Есть подтверждение провайдера; требуется только локальная финализация |
| `completed` | Подтверждение, счет и уведомления зафиксированы; HTML/PDF удалены |
| `canceled` | До первой попытки счет или расписание перестали допускать отправку |
| `rejected` | Провайдер дал окончательный отказ; автоматического повтора нет |
| `reconciliation` | Неизвестный/противоречивый исход, истекшее окно, clock anomaly или исчерпанные попытки |

## Безопасная диагностика

Для первичной диагностики достаточно метаданных, без конверта и адресата:

```sql
SELECT id, team_id, invoice_id, kind, status, attempts,
       first_attempt_at, next_attempt_at, lease_expires_at,
       accepted_at, completed_at, provider_message_id, last_error
FROM public.invoice_email_deliveries
WHERE status <> 'completed'
ORDER BY created_at
LIMIT 100;
```

Не выводить `envelope`, `activity_snapshot`, адреса и provider payload в логи,
Sentry, Redis job data или публичный отчет. При ошибке SQL worker возвращает
обезличенную ошибку без исходных bind parameters.

Для `reconciliation` нужно сопоставление с журналом почтового провайдера.
Нельзя обнулять `first_attempt_at`, менять ключ или снова ставить ту же
операцию на отправку только ради снятия ошибки. Отдельный операторский
интерфейс и проверенный workflow ручного подтверждения/отказа пока не
реализованы. Пока оператор не выяснил исход, остановленная строка остается
остановленной.

Изменение статуса или расписания после последней DB-проверки не отменяет уже
начавшийся HTTP. Новая явная ручная отправка является отдельной операцией;
глобальная дедупликация всех писем по одному invoice ID намеренно не применяется.
