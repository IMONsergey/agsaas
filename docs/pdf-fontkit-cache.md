# PDF glyph metadata after composite subsetting

## Scope and evidence

This patch targets fontkit **2.0.4**, as resolved in the reviewed Bun lockfile,
for the owned Liberation Sans invoice fonts. It does not reset the global
React-PDF font store, alter the fonts, or change document parsing.

The round 7 offline PDF log extracted `OWN-ORRUPT-LOGO` in all three optional
corrupt-logo cases. The earlier test rendered Cyrillic `Счёт` in the same
process. Static inspection establishes this reachable sequence:

1. The invoice template registers its four font sources once. React-PDF's
   process-wide FontStore retains their fontkit objects across documents.
2. In all four bundled TrueType faces, Cyrillic U+0421 is glyph 445, a composite
   containing glyph 38. Latin U+0043 maps directly to glyph 38.
3. fontkit's TTFSubset encodes composite components by calling
   `font.getGlyph(gid)` without source characters. The cached component has
   `codePoints: []`.
4. The original `getGlyph(gid, characters)` cache ignores later characters when
   that glyph ID is already cached. A later Latin C therefore receives empty
   Unicode metadata.
5. React-PDF uses those code points for layout character indices and PDFKit's
   ToUnicode map. PDF.js can fall back to the subset character code when that
   map entry is empty; the application removes C0/C1 control characters.

The final missing-character stage must be checked against the saved failing
PDF from the next controlled render gate. This is a source-supported cause,
not a claim that an unexecuted regression has passed. The three corrupt logo
inputs do not modify invoice text, and parsing uses a fresh child process per
document. `cleanText` cannot remove an actual U+0043 by itself.

## Exact change and concurrency

The version-scoped patch changes only `TTFFont.getGlyph`. If a cached glyph has
zero code points and a later lookup supplies nonempty characters, it removes
that cache entry and runs the existing constructor path. The newly constructed
Glyph receives correct Unicode metadata, `isMark`, and `isLigature`.

Already-returned Glyph objects are not mutated. Concurrent layouts retaining
the previous component object keep its original data and geometry. Replacement
and construction contain no asynchronous boundary. Nonempty cache entries,
lookups without characters, subset IDs, font metrics, and font registration
semantics are otherwise unchanged.

The same small hunk is included in the source and all four package runtime
exports: Node ESM/CJS and browser ESM/CJS. The manifest records the reviewed
original and resulting SHA-256 for every file. Existing dependency source maps
are not regenerated by this narrowly scoped patch.

## Dependency contract

The root `package.json` pins `overrides.fontkit` to `2.0.4` and maps
`patchedDependencies["fontkit@2.0.4"]` to
`patches/fontkit@2.0.4.patch`. Bun documents root package patch declarations
and installation of committed patch files:

- https://bun.com/docs/pm/cli/patch
- https://bun.com/docs/pm/overrides

The declared runtime remains Bun 1.3.11. The repository patch was prepared
from read-only installed bytes; neither a shared node_modules directory nor
Bun's global cache was edited. No install was run. `bun.lock` is deliberately
unchanged in this source packet: the root-controlled install must produce and
review its patch/override lock delta before release. A frozen-lock install and
the actual exported-package regressions are required before accepting it.
Future fontkit upgrades require a reviewed removal or rebase of this patch,
not bypassing failed patch application.

## Controlled validation

Prepared tests:

- `packages/invoice/src/utils/fontkit-cache.test.ts`: four real font faces.
  Encodes a Cyrillic subset, verifies the empty component, then checks correct
  Latin Unicode, identical outlines/metrics, stable populated cache identity,
  and preservation of the old component object.
- `apps/worker/src/processors/invoices/invoice-font-cache.test.ts`: two real
  invoice PDF cases. One renders Cyrillic then Latin in the same process and
  verifies all four faces through the isolated production parser. The other
  starts three PDF renders concurrently and verifies each distinct document.
  Parsing is serial to respect the worker's two-child limit.
- Existing `invoice-pdf-offline.test.ts` remains unchanged. Its exact
  `OWN-CORRUPT-LOGO` assertion must pass for all three malformed logo inputs.

Each new suite runs in its own process. The real PDF suite refuses fetch and
socket traffic; its only inline resource allowance is the exact existing Yoga
WASM hash, and its descriptor allowance matches only the isolated child's
anonymous IPC channel. It uses no provider, SQL, Storage, queue, email, or
payment credentials. No font-store reset is performed. An optional
`AGSAAS_RENDER_ARTIFACT_DIR` retains every generated test PDF before extraction.

No runtime, typecheck, database operation, or test was executed while preparing
this source packet. Runtime acceptance is pending the controlled queue.
