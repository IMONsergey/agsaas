# AGSaaS — implementation backlog

Source: owner-approved 40-block backlog supplied on 2026-10-31. Starting revision: `d95ffa247817c23d855ba178de32bfc987f2c7c1`.

## Execution rules

- Preserve the existing frontend structure, design, and legitimate workflows.
- Each implementation needs focused regression tests; unavailable live/provider checks remain explicitly unverified.
- Do not rewrite the applied self-hosted baseline or run destructive test harnesses against application data.
- Existing private staging is not public production. Domain, external SMTP, provider accounts, legal choices, and off-host backup destination are separate release gates.
- Paused Storage/file-export review remains excluded. No work from that WIP is implicitly included.

## Current implementation packet

- Implemented packet 01: financial query correctness (1), strict import profiles/precision/deduplication (2), transactional team ownership (3), retry-only account deletion and recovery UI (4), permanent-job retry handling and optional-AI search.
- Independent membership candidate review found two blockers (late Auth completion and nested-pool starvation); the implementation now uses a durable deletion marker and no DB transaction across HTTP. Both cases have real PostgreSQL regression tests.
- Verification and deployment evidence, remaining limitations and rollout requirements: [packet 01](agsaas-hardening-packet-01.md).
- No block below is considered complete merely because one subtask has been implemented.

## Owner-approved backlog

1. **Достоверность финансовых расчётов — P0**
   - Исправить агрегаты в списке и карточках клиентов: одновременное объединение счетов, проектов и тегов размножает строки, из-за чего количество документов и суммы могут завышаться.
   - Например, по структуре текущего SQL один оплаченный счёт на 100, два проекта и два тега могут дать итог 400. Нужны независимые агрегаты и регрессионные тесты.
   - Убрать сложение счетов разных валют с отображением валюты первого попавшегося счёта. Либо группировать суммы по валютам, либо выполнять явную конвертацию.
   - Исправить налоговую сводку: явно сохранённый `taxAmount` сейчас учитывается при отборе операций, но не используется в итоговой формуле налога.
   - Зафиксировать единые правила округления, скидок, налогов, отрицательных сумм и возвратов; сверить результаты интерфейса, API и документов.
   - Проверять расчёты на контрольном наборе с заранее известными результатами. Основание: customers.ts и reports.ts.
2. **Импорт банковских выписок — P0**
   - Исправить подтверждённые ошибки парсера: `1 234,56` превращается в `NaN`, а `1,234.56` — в `1.23456` вместо `1234.56`.
   - Ввести явный формат даты: при российском прочтении `01.02.2026` должно означать 1 февраля, но текущий парсер возвращает 2 января.
   - Исправить идентификацию дублей: две разные операции с одинаковыми датой, суммой, описанием и контрагентом сейчас могут получить один идентификатор и схлопнуться.
   - Добавить профиль импорта: кодировка, разделитель колонок, формат даты, десятичный разделитель, валюта, отдельные дебет и кредит.
   - До подтверждения показывать нормализованные значения и предупреждения по неоднозначным строкам; после — понятный отчёт об ошибках, а не только количество.
   - Проверить повторный и частичный импорт, одинаковые реальные платежи, возвраты, пробелы/NBSP и файлы выбранных российских банков. Основание: utils.ts и transform.ts.
3. **Права владельца и участников команды — P0**
   - Зафиксировать понятную матрицу прав для уже существующих `owner` и `member`: управление компанией, участниками, финансами, интеграциями и оплатой.
   - Добавить серверные проверки владельца там, где сейчас проверяется только членство: в частности, для удаления команды и выдачи роли владельца через приглашение.
   - Проверить все способы выполнения действий: интерфейс, REST, tRPC, API-ключи и MCP. Скрытая кнопка не заменяет серверное ограничение.
   - Проверить конкурентные операции с последним владельцем: два одновременных выхода, удаления или понижения роли не должны оставлять компанию без управления.
   - Расширить существующие проверки изоляции команд на остальные модули и фоновые задания. Основание: team.ts.
   - Новые роли вроде «бухгалтер только для чтения» добавлять по реальному сценарию, а не ради усложнения системы.
4. **Удаление аккаунта и компании — P0**
   - Исправить подсчёт участников при удалении пользователя: текущий запрос считает строки после фильтра по удаляемому пользователю, а не фактический размер всей команды.
   - Убрать обязательную зависимость удаления аккаунта от Resend: отсутствие почтового ключа не должно оставлять операцию в частично выполненном состоянии.
   - Согласовать последовательность удаления профиля, Auth-пользователя, членства, подключений и фоновых задач; SQL-транзакция сама по себе не откатывает внешние сервисы.
   - Предусмотреть передачу владения, понятное подтверждение последствий и правила сохранения финансовой истории.
   - Проверить повторный запрос, сбой на каждом этапе и безопасное восстановление после частичного выполнения. Основание: users.ts.
5. **Вход, сессии и двухфакторная аутентификация — P0/P1**
   - Показывать только настроенные способы входа. Сейчас OAuth-кнопки могут отображаться без соответствующей конфигурации, а рабочий email-вход скрыт в дополнительных вариантах.
   - Довести обработку ошибок запуска OAuth: проверять ошибку SDK и гарантированно снимать состояние загрузки.
   - Различать истёкшую сессию и временную недоступность API: действующего пользователя при серверной ошибке не следует отправлять на повторный вход.
   - Проверить неверный и просроченный OTP, повторную отправку, ограничения частоты, двойное нажатие, обновление страницы и возврат назад.
   - TOTP MFA уже есть: нужны собственное название сервиса в приложении-аутентификаторе, проверки подключения, отмены, повторной попытки и восстановления доступа.
   - Уточнить управление сессиями: текущий выход локальный; отдельно нужен поддерживаемый сценарий выхода со всех устройств и понятные сроки отзыва доступа.
   - Проверить изменение email и синхронизацию профиля, приглашений и уведомлений.
6. **Настоящая почта — P0**
   - Подключить реальную доставку вместо capture-only Mailpit: сейчас тестовые письма не приходят в настоящие почтовые ящики.
   - Разделить Auth-почту Supabase и продуктовую почту: приглашения, счета, напоминания и поддержка не становятся рабочими автоматически после настройки одного SMTP.
   - Настроить домен отправителя, SPF/DKIM/DMARC и проверить доставку, задержки и попадание в спам.
   - Подготовить собственные русские шаблоны, корректные ссылки и адреса ответа.
   - Различать «письмо поставлено в очередь», «передано провайдеру» и «не доставлено»; безопасно обрабатывать повторную отправку.

   - Ввести реестр доступности функций: реализована, настроена на сервере, доступна команде, подключена, временно недоступна.

16. **Валюты и курсы — P1**

17. **Выставление счетов — P1**
