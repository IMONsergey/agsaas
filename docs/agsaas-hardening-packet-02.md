# AGSaaS: пакет доработок 02

Основание: приложенный пользователем аудит из 36 пунктов, прежде всего пункты
1–5 и часть пункта 7. Начальная ревизия:
`8661fb229bf249b2213b6e9ca1dc018a299835a4`.

Это ограниченный проверяемый пакет исправлений, не завершение всех 36 пунктов
и не разрешение на публичный запуск финансового продукта. Фронтенд и дизайн
сохраняются; меняется корректность существующих сценариев.

## Реализованные изменения

### 1. Сохранение финансовой истории компании

- `bank_accounts.created_by`, `invoice_recurring.user_id`, `invoices.user_id`
  и `apps.created_by` перестают каскадно удалять записи при удалении профиля.
  Вместо этого исторический автор становится `NULL`. Банковский счёт вместе
  с транзакциями, выставленные счета, серия и настройки приложения остаются
  в своей компании; другой сотрудник не назначается фиктивным автором.
- Два ранее обязательных поля автора становятся nullable. Регулярная серия
  больше не считается повреждённой только из-за удалённого автора. Действующие
  правила прав доступа основаны на компании и текущем членстве, не на авторе.
- Каскад удаления самой компании сохраняется. Личные API-ключи, членство,
  привязки внешней личности и личные OAuth-токены не превращаются в общие.
- Правило действует на уровне внешнего ключа, в том числе для бывшего участника
  без текущего членства и для каскада Auth → профиль. Оно не зависит от того,
  какие команды вспомнил прикладной цикл удаления.
- Immutable baseline не изменяется. Новая CLI-created миграция
  `20261101042940_preserve_team_financial_history.sql` проверяет исходные
  ограничения, ограничивает ожидание блокировок и выполняется транзакционно.

### 2. Денежная сумма и сохранённый финансовый снимок

- Общий расчёт используется на границе сохранения счёта. Переданные клиентом
  итоги для счёта с позициями не считаются источником истины.
- Арифметика десятичных значений не зависит от накопления ошибки binary
  floating point. Сохранён существующий контракт `numeric(10,2)`: subtotal,
  VAT и tax округляются по итогам, фиксированная скидка применяется после
  налогов. Это не универсальная реализация всех ISO валютных exponent.
- Сохранён сценарий API-счёта с суммой без позиций; отсутствие позиций не
  обнуляет такой счёт. Проверяются конечность чисел, диапазон, ставки и
  допустимость количества.
- REST, публичный HTML и PDF используют сохранённый финансовый снимок, не
  придумывают новый итог при чтении старого документа. Исторические суммы не
  пересчитываются миграцией.
- Финансовые изменения уже оплаченного, возвращённого, отменённого счёта или
  счёта с прикреплённым payment intent отклоняются под блокировкой строки.
  Совместимые нефинансовые правки не переписывают его финансовые поля.
- Редактор различает финансовые исходные данные и вычисляемые итоги. Открытие
  старого счёта, правка примечания или срока не пересчитывают его историю.
  Подтверждённый сервером финансовый снимок обновляется после сохранения,
  без сброса новых несохранённых правок. Autosave сериализован; ответы из
  закрытого/сброшенного редактора не подменяют снимок другой формы.
- Для неполных старых шаблонов сохранены стабильные legacy defaults
  калькулятора: VAT/tax включены при отсутствии флага, ставки по умолчанию
  нулевые. Новый шаблон UI по-прежнему явно выключает их. Реквизиты уже
  выпущенного счёта не наследуют изменившиеся финансовые настройки компании.
- Существующее редактирование неоплаченных и просроченных счетов без intent
  сохранено. Версионирование исправлений всех выпущенных документов остаётся
  отдельным продуктовым решением.

### 3. Валюта и поиск

- Валюта проекта при создании счёта из учёта времени имеет приоритет над
  сохранённым шаблоном; числовой итог не маркируется другой валютой.
- Цифровой префикс запроса больше не превращает весь текст в несуществующее
  числовое совпадение. Это исправление поиска, не новая система атомарной
  нумерации счетов.

### 4. Фоновая отправка и финансовый статус

- Отправка заранее пропускает неподходящие конечные статусы; напоминания
  допускаются только для неоплаченного или просроченного счёта.
- Подтверждение отправки — одна команда SQL с tenant-boundary и проверкой
  текущего статуса. Только `draft`/`scheduled` становятся `unpaid`.
  Запоздалый worker не меняет `paid`, `refunded`, `canceled` или `overdue`
  обратно на `unpaid`.
- `sentAt` и `reminderSentAt` фиксируют подтверждённый приём провайдером, не
  помещение задания в очередь. Более старое завершение не откатывает метку
  времени. HTTP-запрос не выполняется под SQL-блокировкой.
- Scheduler больше не переводит счёт в `unpaid` до генерации PDF и не очищает
  ссылку на расписание до подтверждённой отправки. Отказ Redis оставляет
  исходное состояние для повтора, а конкурентная оплата не затирается.
- Новые scheduled handoffs передают точный `expectedScheduledJobId` через
  генерацию PDF в email job. Перенос или отмена, наблюдаемые проверкой версии,
  останавливают старое задание; позднее подтверждение не очищает новый marker.

### 5. Честный результат email

- Ответ SDK с `{ error }` не является успешной отправкой. Результат различает
  принятые, пропущенные, отклонённые и неопределённые конверты; это не гарантия
  доставки во входящие адресата.
- Для invoice delivery успешная activity создаётся после подтверждения
  приёма, а не до попытки. Если activity не сохранилась после приёма письма,
  факт приёма всё равно пытаемся записать в счёт.
- Однозначный временный отказ может повторяться. Неопределённый внешний
  результат и сбой локальной записи после внешнего успеха останавливают
  автоматический resend и требуют сверки, чтобы не плодить письма вслепую.

| Независимое повторное review | Найденные money/editor и scheduled-version regressions исправлены и повторно проверены |

Окончательные TypeScript, PostgreSQL/Redis и чистые Docker-сборки проверяются
для опубликованной ревизии. Их результат и ссылка на конкретный GitHub Actions
run фиксируются в [Draft PR #1](https://github.com/IMONsergey/agsaas/pull/1), а не
подменяются ранними локальными результатами. Локальные unit-тесты без
`TEST_DATABASE_URL` пропускают PG suites — присутствие теста в репозитории не
считается доказательством исполнения SQL.

Для существующего HTTP shutdown regression потребовался разрешённый локальный
loopback listener: ограниченная среда отклоняла `Bun.serve` с `EADDRINUSE` для
порта 0. Полный успешный прогон выполнен с разрешением на этот локальный тест;
он не отключался и не обращался к серверу пользователя.

- Схема: точный SHA-256 установленной baseline и строгая проекция только
  разрешённых incremental изменений; сохранение team cascades.
- Регулярные счета: nullable автор допустим, отсутствующие/повреждённые поля
  не маскируются под анонимизацию; правила обязательных реквизитов сохраняются.
- PostgreSQL: прямое удаление профиля, общий/одиночный состав компаний,
  бывший участник, отказ Auth и повтор, сохранение финансовых связей и
  удаление личных credentials; отдельная репетиция реального SQL-файла.
- Счета: денежная арифметика, диапазоны и округление, API/render contracts,
  запись без позиций, блокировки, foreign-tenant conflict и замороженные суммы.
- Доставка: реальный Resend SDK с перехваченным HTTP, не внешние письма;
  worker retry/error paths и атомарные PG обновления статуса/времени.

Disposable PG в CI не заменяет rehearsal на совпадающей версии Supabase с
настоящим Auth, RLS и HTTP-входом. Проверка Docker на сервере остановилась на
отказе доступа к сокету для `sergey`. Административный доступ не использован;
рабочая БД и серверная версия в этом пакете не обновлялись.

## Незакрытые P0 и следующие пакеты

1. **Онлайн-платежи (пункт 6).** До прикрепления первого payment intent остаётся
   окно между чтением суммы, внешним запросом Stripe и SQL-записью intent.
   Нужны reservation/version/conditional attachment, безопасная отмена stale
   intent, журнал provider events, out-of-order и частичные возвраты. Этот
   пакет не объявляет online checkout готовым. Существующий status API также
   разрешает ручное повторное открытие конечного счёта: текущий financial
   guard не заменяет историческую неизменяемость и полную state machine.
2. **Outbox и восстановление (пункт 12).** Нет общей атомарности SQL + Redis +
   HTTP. Падение процесса после приёма письма, но до локальной записи, всё ещё
   требует устойчивого delivery envelope, idempotency key и reconciliation.
   Один ключ без сохранённого неизменного payload недостаточен: ссылки и
   случайные email headers меняются между попытками.
   Новый version marker защищает scheduled handoff, но не создаёт атомарности
   между последним чтением БД и внешней отправкой. Окно включает подготовку
   notification и HTTP; уже начавшуюся отправку он отменить не может.
3. **Полный lifecycle интеграций (пункт 1).** `oauth_applications.created_by`
   всё ещё каскадно удаляет командный client definition и связанные токены
   других пользователей. Это отдельный дефект, не исправленный автоматически
   четырьмя финансовыми FK. Требуются собственная политика владения и тесты.
4. **Провайдерские grants и персональные данные.** Сохранение `apps` не обещает
   действительность внешнего токена и не анонимизирует произвольный settings
   JSON. Report/share links сохраняют текущую политику отзыва по автору;
   исходные финансовые транзакции от этих report cascades не удаляются.
5. **Обновление и выпуск (пункты 20, 23, 27).** До rollout нужны проверенный
   backup/restore, matched-stack migration rehearsal, инвентаризация версии
   серверного приложения и сквозные браузерные сценарии.

Storage/export остаётся отдельной приостановленной областью. Этот пакет не
возобновляет отложенную ветку и не делает выводов о готовности файловых
сценариев. Остальные пункты аудита не считаются закрытыми из-за зелёной сборки.

## Развёртывание

Порядок, maintenance locks и ограничения отката описаны в
[incremental upgrades](../packages/db/self-hosted/upgrades/README.md).
Baseline нельзя переписывать; Drizzle `push` допустим только в защищённой
disposable test DB. Сначала завершить CI и rehearsal, затем согласовать
серверный административный запуск. Не менять рабочие VPN/443 ради стенда.

Перед обновлением остановить создание/исполнение invoice jobs и проверить
старые `generate-invoice` / `send-invoice-email` задания в Redis. Ранее
поставленные задания без `expectedScheduledJobId` нельзя отличить от
допустимой ручной/регулярной отправки; совместимость намеренно сохранена.
Нужны их контролируемое завершение или сверка/пересоздание из актуального
расписания, не слепое удаление всей очереди. Защита версии не применяется
ретроактивно к старому payload.
