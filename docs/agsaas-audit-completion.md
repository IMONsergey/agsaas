# AGSaaS: результаты исправлений аудита, packet 05

Документ фиксирует реализованный кандидат и подтвержденные проверки на 2026-11-01.
Он не подтверждает применение миграций или публикацию этого кандидата в работающей установке.
Результаты восстановления и репетиции миграций приведены ниже. Итоговая общая проверка типов, сборки Docker и браузерная приемка фиксируются после фактического выполнения в release review.

## Безопасность: SEC01-SEC10

| Группа | Реализованное поведение |
| --- | --- |
| SEC01 | Общая строгая проверка ключей private vault согласует проверяемый и используемый путь. Новые PDF получают ключ по неизменяемому UUID счета. |
| SEC02 | JWT API проверяет действующие MFA-факторы через Auth. Для пользователя с MFA требуется AAL2; ошибка проверки закрывает доступ. API key и OAuth сохраняют отдельные правила scopes. |
| SEC03 | Публичные JSON/PDF endpoints не раскрывают draft, scheduled и canceled. Защищенный просмотр собственного draft остается доступен владельцу с правами команды. |
| SEC04 | Пользовательские endpoints больше не выдают file key через чужой scope. Контекст команды определяется полномочиями использованного credential. |
| SEC05 | File key v2 действует 300 секунд и связан с user/team/aal. Чтение заново проверяет профиль, членство и MFA; старые team-only ключи отклоняются. |
| SEC06 | OAuth revoke отзывает access token и семейство refresh tokens с проверкой принадлежности клиенту. |
| SEC07 | Погашение authorization code и ротация refresh token выполняются атомарно: при конкурентном обмене выигрывает один запрос. |
| SEC08 | Inbox OAuth использует одноразовый SQL intent на 10 минут, хешированный state и браузерный nonce. Callback повторно проверяет пользователя, команду, источник, провайдера и MFA. |
| SEC09 | Удаление банковского подключения, команды или одиночного аккаунта атомарно создает зашифрованное задание отзыва у провайдера. Оно переживает удаление исходных строк и сбой Redis. |
| SEC10 | Отображение приватных изображений не передает file key стороннему сервису обработки изображений. |

Проверка file key обеспечивает отзыв доступа по состоянию пользователя и членства.
Она не обещает отзыв каждого уже выданного ключа при любом выходе из отдельной браузерной сессии.
Машинные credentials не превращаются в интерактивные MFA-сессии.

## Финансовые сценарии: FIN01-FIN09

| Группа | Реализованное поведение |
| --- | --- |
| FIN01 | Номер выдается атомарно внутри команды; уникальный индекс защищает конкурентные записи. UUID ключ PDF исключает перезапись другого счета с тем же отображаемым номером. |
| FIN02 | Billing включается явной настройкой, использует собственные Polar products и полномочия владельца. Действующая подписка управляется через собственный portal; webhook проверяет customer/team/product и порядок версий подписки. |
| FIN03 | Recurring invoice, изменение периода и SQL intents для очереди фиксируются одной транзакцией. Повторный или устаревший scheduler не продвигает период второй раз; scanner восстанавливает передачу после сбоя Redis. |
| FIN04 | Время резервируется за одним draft invoice с сохранением секунд, ставки и валюты. Удаление невыставленного draft освобождает резерв; выставленный документ сохраняет привязку. Изменение уже выделенного времени блокируется. |
| FIN05 | Ставка и валюта сохраняются в записи времени. Изменение проекта не переоценивает существующую работу; разные валюты требуют отдельных счетов. |
| FIN06 | Итоги периода учитывают часовой пояс и только пересечение интервала с запрошенным диапазоном, включая переходы суток и DST. |
| FIN07 | Start/stop сериализуются по команде и исполнителю. Частичный уникальный индекс запрещает второй работающий таймер; проверки принадлежности команды сохранены. |
| FIN08 | Одиночное ручное создание транзакции использует стабильный operation UUID. Повтор возвращает прежний результат, другой payload конфликтует; SQL intents последующих задач создаются атомарно. Удаление сохраняет защиту от воскрешения старым retry. |
| FIN09 | При выставлении сохраняется неизменяемый снимок документа. Публичный просмотр и генерация PDF используют его; финансовая идентичность блокируется, текущие статусы оплаты остаются актуальными. Исправление оформляется дубликатом. |

Для старых документов `legacy_current` означает состояние, доступное на момент миграции.
Это не реконструкция ранее отправленного PDF и не доказательство совпадения с его байтами.
Для старого времени уже записанные условия сохраняются, недостающие берутся из текущего проекта с той же явной отметкой происхождения.
Миграция не выдумывает исторические ставки или привязки ранее выставленных часов.
Стабильный operation UUID относится к одиночному ручному созданию; bulk/import сохраняют отдельный контракт.

## Интеграции и продуктовые ограничения

- Product mail использует собственные `EMAIL_FROM`, `EMAIL_REPLY_TO`, `APP_NAME` и dashboard URL. Отсутствие конфигурации проверяется до расходования попытки invoice/invitation outbox; замороженные тело и ключ сохраняются.
- Generic notifications получили SQL журнал, восстановление и различение подтвержденного приема, отказа и неизвестного исхода. Polar payment-issue intent создается в транзакции изменения подписки.
- Inbox manual sync, удаление, scheduler, статус задачи и начальная обработка callback используют собственную BullMQ очередь с проверками команды и жизненного цикла подключения.
- Банковский cleanup хранит credentials только в зашифрованном SQL payload. При подтвержденном завершении ciphertext удаляется; неизвестный исход переводится на ручную сверку.
- Capability API и UI сообщают об отсутствии конфигурации. Собственные avatar/logo URL, MCP origin и inbound address больше не требуют чужой установки. Наличие конфигурации само по себе не подтверждает работоспособность провайдера.
- Password sign-in и смена пароля доступны по настройке. Смена проверяет текущий пароль отдельным временным клиентом и использует исходную MFA-сессию. Recovery требует отдельного явного включения и реального Auth SMTP.
- Support/feedback используют ограниченный по времени и размеру GraphQL transport Plain. Успех показывается только при подтвержденном thread ID; при неопределенном результате автоматической повторной отправки нет.
- Убраны чужие support-контакты, ссылки в публичных footers и неподтвержденные заявления о сертификации. При ненастроенной поддержке UI направляет к владельцу workspace без вымышленного адреса.
- Обновлены зависимости и адаптеры к их текущим контрактам, включая BullMQ Redis client, MCP и support transport. Полный Storage/export WIP остается приостановленным; в этом пакете проверяется собственный private vault для счетов.

## Шесть миграций и неизменяемый baseline

Packet 05 добавляет шесть последовательных upgrade migrations: notification dispatch, Inbox OAuth intent, invoice/tracker integrity, financial handoff/allocations, bank cleanup и порядок событий подписки.
Полные имена, порядок и условия применения приведены в [upgrade README](../packages/db/self-hosted/upgrades/README.md#packet-05-audit-fixes).
Исходный `20261031154237_application_baseline.sql` не переписывается.
Его SHA256: `e999657a93946bc8de87cc3a9321757984cfe2e3b3491fa643be58f10b8b32fd`.

Повторяющиеся номера счетов и несколько работающих таймеров требуют явной сверки до миграции.
Проверка останавливает upgrade без удаления, перенумерации или автоматического закрытия исторических записей.
Применение требует резервной копии, восстановления на изолированной копии, проверки ACL и точного SQL в migration ledger.
Schema push на работающей базе не является способом обновления.

## Открытые проверки перед включением возможностей

1. Завершить общий type gate и Docker builds, затем выполнить rollout и браузерную приемку именно опубликованной версии. Unit checks, восстановление DB/config/private Storage и репетиция всех шести upgrades уже выполнены; текущие release результаты находятся в PR 1.
2. Настроить собственный Resend sender и отдельно Auth SMTP. Сейчас внешняя почта не настроена, recovery выключен. Приемка требует доставки в собственный ящик; Mailpit этого не доказывает. Реальных отправок провайдерам в рамках этих исправлений не выполнялось.
3. Сохранить recovery выключенным до проверки письма, PKCE callback в том же браузере, MFA и смены пароля. Не подменять эту проверку административным созданием сессии или подтверждением пользователя.
4. Подключать банки только после настройки самого провайдера и оставшегося Trigger runtime. Полная банковская синхронизация еще не перенесена на собственную очередь. Gmail/Outlook требуют реальной настройки приложений и приемки OAuth отдельно от SQL/HTTP fixtures.
5. Billing остается opt-in. Полный Polar sandbox lifecycle не проверен; `subscription.updated` и `subscription.uncanceled` не покрыты этим пакетом. Старые подписки с неизвестной привязкой требуют сверки до включения, а не предполагаемого восстановления ID.
6. Неизвестные или частично подтвержденные результаты внешних отправок и cleanup требуют ручной сверки. Не менять idempotency key и не сбрасывать журнал попыток для обхода этой границы. Не менять банковский provider account/environment или ключ шифрования при нерешенных cleanup intents без сохранения возможности их завершить.
7. Отдельно принять политику догоняющего recurring billing, полного payment/refund ledger, сверки и экспорта. Этот пакет не добавляет отсутствующую историю расчетов и не возобновляет приостановленный Storage/export WIP.
